# 项目亮点与面试指南

> 本文档提炼项目的可讲述亮点，给出简历 bullet 思路与面试高频问题的答题框架。
> 所有数字均可在仓库中复现（experiments/ 两篇实录、reports/ 示例产物、84 个测试）。

---

## 1. 一句话版本

> 设计并实现了一个零依赖、可迁移的 Agent 评测框架，并用它对 Text-to-SQL 数据分析 Agent 做了一套完整的企业级评测实践：67 条五层评测集、四类评分器、pass@k 指标体系、run 对比与发布门禁、失败回流闭环，CI 全链路无需 API Key 即可复现。

## 2. 亮点清单（按含金量排序）

1. **可迁移的架构抽象**：评测核心与被测对象解耦（Target 协议），接新 Agent 只需一份 JSON 配置或约 20 行代码；数据集/评分器/指标/门禁全部复用。这是"做过平台"和"写过脚本"的分水岭。
2. **确定性的质量判断**：事实正确性交给 reference SQL 执行比对（行级 diff + 启发式归因），LLM-as-Judge 只评表达质量且必须过人工校准（Cohen's Kappa）——知道"Judge 不可全信"并给出工程化解法。
3. **时间不变量评测集**：所有相对时间锚定 as_of、种子数据固定随机种子，任何机器任何日期重跑逐行一致——可复现性是评测的生命线。
4. **门禁双机制**：绝对阈值（safety 零容忍）+ 相对基线回归（退步即拦截），指标缺失按不通过处理；CI 真实拦截有实录（mock:flawed 被拦，core 跌 80pp）。
5. **失败归因词汇表**：E1–E15 失败分类法贯穿评分器、报告、diff、回流，把"挂了"变成"为什么挂"。
6. **失败回流闭环**：harvest 把失败 trial 一键草稿化为回归用例，lint 持续跟踪未处理草稿——线上失败 → 离线回归的工程闭环。
7. **无 Key 完整演示**：mock 双人格（good/flawed 确定性变换）让面试现场 1 秒跑完全量 201 trials 并演示门禁拦截，不依赖网络与配额。

## 3. 简历 bullet 思路

写法要点：**动作 + 技术决策 + 可量化结果**，避免"负责……参与……"。

参考 bullet（按简历篇幅选用）：

- 设计并实现零依赖 Agent 评测框架（Python 纯标准库），抽象 Target 协议使评测核心与被测对象解耦，接入新 Agent 仅需一份配置或约 20 行代码；
- 构建 67 条五层 Text-to-SQL 评测集（核心/鲁棒/边界/安全/回归），全部用例携带可执行 reference SQL 真值，以固定种子与时间锚定保证跨机器逐行复现；
- 实现四类评分器（代码断言/执行结果比对/LLM-as-Judge/人工校准）与 E1–E15 失败分类法，失败归因细化到行级 diff 与口径方向提示；
- 建立 pass@1/pass^k/Wilson 置信区间指标体系与 run 注册表，支持任意两次实验的指标差与逐 case 翻转对比；
- 实现"绝对阈值 + 基线回归"双机制发布门禁并接入 GitHub Actions，CI 全程无需 API Key，缺陷注入实验（pass@1 16.2%）被门禁稳定拦截；

## 4. 面试高频问题与答题框架

### Q1：为什么不用 LangSmith / Braintrust 这些现成平台？

**框架**：承认价值 → 说清边界 → 讲明权衡。

> 现成平台在 Trace 采集与看板上很成熟，生产环境我会用。但三件事它们给不了：一是 Text-to-SQL 的事实判断需要"在种子库上执行 reference SQL 做结果集比对"，这必须自建；二是我想把"执行比对、执行比对、执行比对"这个核心环节吃透——自己实现一遍 Wilson 区间、Kappa、门禁状态机，比调 API 学到的多得多；三是零依赖让评测可以嵌进任何 CI 而不引入平台锁定。README 里有一张诚实的功能对照表，本项目不假装替代它们。

### Q2：LLM-as-Judge 的可信度怎么保证？

**框架**：限制职责 → 结构化 → 校准闭环。

> 首先 Judge 不判事实——数字对不对由 reference SQL 执行比对决定，Judge 只评四个表达维度。其次 rubric 结构化：每维度 0/1 加理由，输出可解析。最后必须过人工校准：export-labels 抽样 → 盲标 → calibrate 算 Cohen's Kappa，Kappa < 0.4 就重修 rubric 而不是硬用。Judge 无 Key 时三态跳过，不冤枉也不放水。

### Q3：测试集怎么防泄漏 / 防过拟合？

**框架**：污染途径分析 → 机制防线 → 流程防线。

> 泄漏有三条途径：数据进训练集、评测脚本被 Agent 读到、人看着测试集调 prompt。机制上：种子数据是合成电商数据而非真实数据；reference SQL 只存在 datasets 里、不进 Agent 的系统提示（只给口径字典）；dataset_hash 随 run 记录，数据集被改动后旧基线自动不可比。流程上：回归层用例来自真实失败回流而非拍脑袋新增；prompt 调优只看 core/robustness 层，edge/safety 层作为"held-out"少看。

### Q4：指标阈值是怎么定的？

**框架**：分层逻辑 → 数据驱动 → 联动样本量。

> safety 是 1.0 没有谈判空间；core 0.85 是"当前水位 − 5pp"的经验起点，随改进抬升；max_drop_pp=2.0 与样本量联动——core 25 条 × 3 trials 时一条 case 翻转约 4pp，2.0 意味着"不允许任何一条全过的 case 挂掉"。阈值每次调整都进 commit message 接受审计。详细推导在 docs/ci_gate.md 第 5 节。

### Q5：pass@1 和 pass^k 为什么都要？

> pass@1 度量"单次出手可不可靠"——生产视角，用户只体验一次；pass^k 度量"k 次里至少成功一次的能力上限"——能力视角，两者差距大说明结果方差大、提示词或采样有改进空间。配 Wilson 置信区间判断差异是否显著，避免对着噪声调优。

### Q6：如果让你继续做，下一步是什么？

> 三件事：真实模型全量对比（命令与模板已备好，配 Key 即跑）；Judge 校准实录（产出真实 Kappa 并据结论迭代 rubric）；把 Target 样例扩到 RAG 场景，验证协议在非 SQL 领域的迁移成本——那才是"可迁移"这三个字真正的考试。
